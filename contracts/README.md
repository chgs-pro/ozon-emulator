# Контракт Seller API

Эмулятор проверяет каждый запрос и каждый свой ответ по описанию Seller API. Описание взято из OpenAPI-файла,
который поставляется с PHP SDK [`phpsoftbox/ozon`](https://github.com/phpsoftbox/ozon) (`docs/swagger.json`).
Из него вырезаны только нужные методы со всеми связанными схемами, без правок, — это и есть «профили»:

| Файл | Что внутри | Методов |
|---|---|---|
| `fbo.json` | FBO: кластеры и склады, черновики, заявки и поставки, грузоместа и ТГМ, этикетки, изменения, отмена, акты; товары и роли | 54 |
| `fbs.json` | FBS: склады продавца, остатки, отправления, отмена, экземпляры, сборка, этикетки | 30 |
| `catalog.json` | Категории, атрибуты и характеристики товаров | 3 |

В каждом файле записаны commit SDK и SHA-256 исходного описания, из которого он собран. Во время работы эмулятор
читает только эти файлы, SDK ему не нужен. Метод, которого нет в профилях, отвечает 404 — эмулятор не отдаёт
выдуманных «успешных» ответов.

## Как проверяются запросы

Проверяются структура, обязательные поля, типы, допустимые значения (enum), диапазоны, размеры списков и формат
дат. Связи между объектами и их состояние проверяет уже логика эмулятора. В нескольких схемах Ozon у списков и
объектов не указан `type` — валидатор определяет его по `items` и `properties`. Это валидатор для используемого
подмножества OpenAPI, а не универсальная реализация.

Ответы эмулятора тоже проверяются по профилю, поэтому он не может незаметно вернуть поле не того типа.

## Как пересобрать профиль

После обновления SDK (`composer update phpsoftbox/ozon`) профиль собирается заново с тем же набором методов:

```bash
python3 tools/build-contract.py fbs $(python3 -c "import json; print(' '.join(json.load(open('contracts/fbs.json'))['paths']))")
```

Чтобы добавить метод, допишите его путь в конец команды. Скрипт можно запускать из любой папки.

## Допущения

Описание API Ozon местами противоречиво или неполно. Где эмулятору пришлось выбирать, решения перечислены ниже.

### Общие

- Поля `int64` в запросах принимаются и числом, и десятичной строкой: SDK отправляет оба варианта. В ответах тип
  берётся из схемы.
- Название роли в `/v1/roles` берётся из конфигурации (`Admin` в готовых наборах), а список методов — из того, что
  реально поддерживается и разрешено кабинету (`writeEnabled`). Это не подтверждает права настоящего кабинета.

### FBO

- `storage_warehouse_id` при создании поставки нужен только для DIRECT. Схема помечает его обязательным для всех,
  но описание поля — нет; для CROSSDOCK и MULTI_CLUSTER склад выбирает расчёт.
- В черновиках используются ID кластеров из API v2 (`macrolocal_cluster_id`); ID из v1 задаются в конфигурации отдельно.
- Поиск складов возвращает `WAREHOUSE_TYPE_*`, а черновик принимает короткое название типа.
- Квант (`quant`) — кратность количества; остаток, который не делится на квант, отклоняется по правилу
  `FULL`/`PARTIAL`. Точную семантику для реальных категорий нужно проверять на Ozon.
- В схеме `/v1/cargoes/label/transport/status` опечатка: обязательное поле `operation_idd`. Принимается
  `operation_id`, как в свойствах схемы и в SDK.
- У методов pass, timeslot, cancel, content и cargo свои форматы статусов и ошибок. Ошибка УПД в статусе изменения
  состава называется `HAS_UTD`, а в `details` — `UTD_IS_UPLOADED`. Эмулятор не сводит их к одному формату.
- Неизвестный статус заявки или поставки допускается только в ответах и задаётся событием; при нём изменения
  блокируются.
- `can_set` в `details` учитывает состояние, дедлайн (за час до слота) и загруженный УПД. `READY_TO_SUPPLY`
  рассчитывается по грузоместам, документам и `vehicleRequired`; физические статусы задаются событиями.
- Лимиты грузомест настраиваются (`cargoLimits`): по умолчанию 1500 коробок, 100 SKU в коробке, 40 паллет,
  40 ТГМ; за запрос — 30 коробок или 40 паллет.
- Этикетки — синтетический PDF 100 × 150 мм с Code 128 `OZTEST<id>`.
- Приёмка создаёт основной акт и отдельные акты расхождений; денежные поля не заполняются; акт не принимается
  автоматически.
- `item_tags_calculation` возвращает теги из конфигурации, а не расчёт по реальным категориям.

### FBS

- `/v2/products/stocks`: схема требует `quant_size`, но такого поля в ней нет — требование снято. `product_id`
  не обязателен при переданном `offer_id`: по описанию метода при обоих полях используется `offer_id`. Лимит
  100 пар и ошибки отдельных строк проверяет эмулятор.
- `/v2/product/info/stocks-by-warehouse/fbs`: условие «`sku` или `offer_id`» (`oneOf`) валидатор не поддерживает;
  эмулятор требует хотя бы один фильтр, как SDK, а при обоих объединяет результаты.
- `/v6/fbs/posting/product/exemplar/set` и `/v1/fbs/posting/product/exemplar/update` описывают ответ 200 без
  схемы; скрипт сборки подставляет пустой объект, эмулятор отвечает `{}`.
- Коды ошибок остатков (кроме `TOO_MANY_REQUESTS`) и проверки экземпляров, справочники пунктов, слотов и стран,
  правило «страна не Россия → нужна ГТД», диапазон веса, штрихкоды этикеток и модель частичной сборки выбраны
  эмулятором. Структурные ошибки `set` и попытка собрать неготовое отправление отклоняются сразу (400).
  Подробнее — в [FBS](../docs/fbs.md).

### Каталог

- Типы товаров отдаются дочерними элементами своей категории, как у Ozon.
- Атрибуты не словарные: `dictionary_value_id` всегда 0. Обязательность, группы и сложные атрибуты не моделируются.

## Что это не проверяет

Профиль — это снимок описания API на момент версии SDK, а не проверка живого Seller API. Поведение настоящего
Ozon может отличаться от описания; такие отличия нужно проверять на реальном кабинете.
