# Тестовый кабинет

Всё, что делает эмулятор, происходит внутри тестового кабинета. Кабинет — это аналог личного кабинета продавца
в Ozon: у него есть Client ID, ключи API, товары, склады, настройки и данные (поставки, отправления, остатки).
Кабинеты изолированы друг от друга: запрос с ключом одного кабинета не видит и не меняет данные другого.

Для независимых сценариев удобно заводить отдельные кабинеты: например, `1001` для ручной проверки и
случайный ID для автотеста.

Все команды ниже запускаются из корня Workspace. Если эмулятор подключён в другое окружение,
замените `docker compose exec php-cli` на свой способ запустить `php psb` в контейнере эмулятора.

## Ключи API

Ключи выдаются только из командной строки — HTTP-метода для этого нет:

```bash
docker compose exec php-cli php psb ozon:token:issue 1001 --ttl-days=30
```

Команда печатает `client_id`, `api_key` и `expires_at`. Ключ показывается один раз — сохраните его.
Срок действия — от 1 до 365 дней (по умолчанию 30). Новый ключ не отменяет старые: каждый действует до своего срока.
В базе хранится только хеш ключа.

Запросы подписываются так же, как в Ozon, — заголовками `Client-Id` и `Api-Key`:

```bash
curl -s http://localhost:8080/v1/roles -H 'Client-Id: 1001' -H "Api-Key: $KEY" -d '{}'
```

Для проверки ключа есть служебный метод, которого нет в Ozon:

```http
GET /test/v1/identity
Client-Id: 1001
Api-Key: <ключ>
```

Неверный ключ, чужой Client ID или истёкший срок дают 401. Ключи эмулятора не подходят к настоящему Ozon, и наоборот.

## Конфигурация кабинета

Кабинет описывается JSON-файлом и загружается командой:

```bash
docker compose exec php-cli php psb ozon:fbo:configure 1001 --file=fixtures/fbs-basic.json
```

Файл проверяется целиком; если в нём ошибка, ничего не сохраняется. Повторная загрузка того же файла ничего не
меняет. Изменённый файл создаёт новую версию настроек: уже созданные поставки, отправления и операции остаются.

Готовые наборы:

| Файл | Что внутри |
|---|---|
| [`fixtures/fbo-basic.json`](../fixtures/fbo-basic.json) | 10 товаров, два кластера, склады и точка сдачи, маршруты DIRECT / CROSSDOCK / MULTI_CLUSTER, каталог категорий |
| [`fixtures/fbo-required.json`](../fixtures/fbo-required.json) | То же с усложнениями для FBO: квант 2, срок годности, маркировка, УПД, обязательная машина, лимиты |
| [`fixtures/fbs-basic.json`](../fixtures/fbs-basic.json) | Базовый набор плюс FBS: два склада продавца, товары с маркировкой |

Основные поля (полный пример — в наборах выше):

| Поле | Смысл |
|---|---|
| `schemaVersion` | Всегда `1` |
| `fboEnabled` | Доступны ли методы FBO; при `false` они отвечают 403 |
| `contractActive` | Активен ли договор FBO; без договора расчёт, создание и изменение поставок заканчиваются ошибкой |
| `writeEnabled` | Разрешены ли методы записи. При `false` кабинет работает только на чтение, а `/v1/roles` не показывает методы записи |
| `roleName` | Название роли в `/v1/roles` |
| `clockOffsetSeconds` | Сдвиг часов кабинета относительно реального времени (см. «Время» ниже) |
| `operationDelaySeconds` | Через сколько секунд завершаются асинхронные операции: расчёты, создание, проверки, этикетки |
| `draftLifetimeSeconds` | Срок жизни черновика FBO-поставки |
| `draftFailure`, `supplyFailure` | Расчёт черновика или создание поставки завершатся ошибкой |
| `fault` | Искусственный сбой транспорта для одного метода — см. «Сбои» ниже |
| `products` | Товары: `sku`, `productId`, `offerId`, название, штрихкоды, объём, квант, теги, габариты, атрибуты |
| `warehouses`, `clusters`, `routes`, `slots` | Справочники FBO — см. [FBO: создание поставки](fbo.md) |
| `catalog` | Дерево категорий и атрибуты — см. [Каталог](catalog.md) |
| `fbs` | FBS: склады продавца, ассортимент и требования к маркировке — см. [FBS](fbs.md) |

ID в конфигурации — положительные целые числа. Имена полей конфигурации записываются в camelCase; в самих запросах
и ответах API используются имена полей Ozon.

## Время

У кабинета свои часы: реальное время плюс `clockOffsetSeconds`. По ним считаются сроки черновиков, слотов,
готовность асинхронных операций и даты отправлений. Часы можно перевести вперёд управляющим событием
`advance`, не дожидаясь реального времени. Срок действия API-ключей всегда идёт по реальным часам.

Асинхронные операции не держат HTTP-запрос: эмулятор запоминает время готовности и завершает операцию
при следующем запросе к кабинету. Поэтому перезапуск сервиса не теряет принятые операции.

## Сбои

Поле `fault` конфигурации имитирует сбой сети или шлюза для одного метода:

```json
"fault": {"path": "/v2/draft/supply/create", "phase": "after", "status": 504, "remaining": 1}
```

- `phase: before` — запрос не выполняется, клиент получает ошибку;
- `phase: after` — действие выполнено и сохранено, но клиент всё равно получает ошибку. Так проверяется,
  что клиент после таймаута сверяет результат, а не повторяет запрос вслепую;
- `status` — 429, 503 или 504; `remaining` — сколько запросов подряд затронет сбой.

Это имитация ответа шлюза, а не настоящий обрыв соединения. Автоматического ограничения частоты запросов, как
в Ozon, нет: ответ 429 задаётся только таким сценарием.

## Управляющие события

Внешние события — то, чего продавец не делает через API: приёмка на складе Ozon, смена статуса, сбой
конкретной операции — задаются командой `ozon:fbo:control`. Seller API к ним доступа не даёт.

```bash
# Журнал кабинета: последние события, ID объектов и операций
docker compose exec php-cli php psb ozon:fbo:control 1001

# Применить событие из файла
docker compose exec php-cli php psb ozon:fbo:control 1001 --file=fixtures/events/partial-cargo.json
```

Каждое событие — JSON с уникальным `eventId` и типом `type`. Повтор того же события безопасен и ничего не делает;
тот же `eventId` с другим содержимым отклоняется. Для нового запуска сценария возьмите новый `eventId`.

Общие события:

| `type` | Поля | Что делает |
|---|---|---|
| `advance` | `seconds` | Переводит часы кабинета вперёд |
| `beta` | `disabledPaths` | Перечисленные методы начинают отвечать 403 — как недоступные в кабинете бета-методы. Пустой список снимает ограничение |
| `reset` | `clientId` (должен совпадать с аргументом команды) | Удаляет данные кабинета: поставки, отправления, остатки, созданные склады. Конфигурация и ключи остаются, ID не переиспользуются |

События для FBO описаны в [FBO: грузоместа, документы и приёмка](fbo-operations.md#управляющие-события),
для FBS — в [FBS](fbs.md#управляющие-события).

## Хранение

Кабинет хранится одним документом MongoDB (`fbo_cabinets`, `_id` = Client ID) с номером версии.
Одновременные изменения не затирают друг друга: при конфликте изменение повторяется над свежей версией.
Размер документа ограничен 12 МБ: при превышении сервис отвечает 507 и ничего не меняет — используйте
другой кабинет. Эмулятор рассчитан на функциональные проверки, а не на нагрузочные.

Журнал хранит последние 200 событий кабинета без ключей и тел запросов.
