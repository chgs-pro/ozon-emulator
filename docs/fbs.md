# FBS: склады, остатки, отправления, сборка, этикетки и отгрузки

FBS — схема, при которой товар хранится на складе продавца, а Ozon присылает заказы (отправления), которые
продавец собирает и передаёт в доставку. Эмулятор умеет:

- **склады продавца** — из конфигурации и созданные через API, с асинхронным созданием;
- **остатки** — публикация и чтение по складам, резерв под отправления;
- **отправления** — генерация тестовых заказов, списки, чтение, поиск по штрихкоду;
- **отмену** — целиком и по товарам, с причинами;
- **требования и экземпляры** — маркировка «Честный ЗНАК», страна изготовления, ГТД, РНПТ, вес, IMEI, УИН;
- **сборку** — целиком, с разделением на упаковки и частично;
- **этикетки** отправлений — асинхронные задачи и PDF;
- **отгрузки** (`carriage`) — создание, состав, подтверждение, статус документов и передача водителю.

Документы отгрузки — синтетический PDF листа отгрузки (`/v2/posting/fbs/act/get-pdf`).

## Включение

FBS включается разделом `fbs` конфигурации кабинета (готовый набор — [`fixtures/fbs-basic.json`](../fixtures/fbs-basic.json)):

```json
"fbs": {
  "enabled": true,
  "warehouses": [
    {"id": 1020001, "name": "Тестовый склад FBS Москва", "status": "created", "firstMileType": "DROP_OFF",
     "deliveryMethods": [{"id": 1030001, "name": "Ozon Логистика, сдача в ПВЗ, Москва"}]}
  ],
  "productSkus": [910001, 910002],
  "markedSkus": [910002]
}
```

Без раздела или при `enabled: false` методы FBS отвечают 403 и не показываются в `/v1/roles`.

Склад в конфигурации:

- `firstMileType` — как товар попадает к Ozon: `DROP_OFF` (продавец сам сдаёт в пункт, по умолчанию) или `PICK_UP`
  (забирает курьер). Для `DROP_OFF` можно указать `dropOffPointId` — пункт из справочника `1040001`–`1040004`
  (ПВЗ, ППЗ, сортировочный центр). По умолчанию `1040001`, для склада крупногабаритных товаров (`is_kgt`) — `1040004`.
- `address`, `latitude`, `longitude` — адрес и координаты; по умолчанию «Тестовый адрес склада <id>» и центр Москвы.
- `deliveryMethods` — методы доставки склада.

Ассортимент и требования — списки SKU из `products`:

| Поле | Что значит |
|---|---|
| `productSkus` | Товары, которые продаются по FBS; пустой список — весь каталог |
| `markedSkus` | Нужна маркировка «Честный ЗНАК» |
| `possibleMarkSkus` | Маркировку можно передать, но не обязательно |
| `countrySkus` | Нужно указать страну изготовления |
| `gtdSkus` | Нужен номер таможенной декларации (ГТД) |
| `rnptSkus` | Нужен регистрационный номер партии (РНПТ) |
| `weightSkus` | Нужен фактический вес каждой единицы |
| `imeiSkus` | Нужен IMEI |
| `jwUinSkus` | Нужен УИН ювелирного изделия |
| `multiboxSkus` | Многокоробочный товар: до сборки у отправления `is_multibox: true`, количество коробок передаётся в `multi_box_qty` набора экземпляров |

Требования попадают в отправление при его создании (`requirements` и `optional` в ответах) и потом меняются только
управляющим событием. Если у отправления есть хоть одно требование, кроме необязательной маркировки, в его действиях
вместо `ship` будет `ship_with_additional_info`.

`warehouseCreateFailure: true` заставляет создание склада через API завершаться ошибкой.

## Склады продавца

`/v2/warehouse/list` отдаёт склады из конфигурации и созданные через API. У каждого склада, как у Ozon, есть
первая миля: пункт сдачи и слот для `DROP_OFF` или слот курьера для `PICK_UP`, а также адрес.

Создание склада асинхронное:

```text
DROP_OFF                                             PICK_UP
/v1/warehouse/fbs/create/drop-off/list               /v1/warehouse/fbs/create/pick-up/timeslot/list
  → пункты 1040001…1040004                             → слоты курьера 1050001…1050003
/v1/warehouse/fbs/create/drop-off/timeslot/list      /v1/warehouse/fbs/return-mile/check → нужен пункт возврата
  → два слота пункта                                 /v1/warehouse/fbs/create/return-point/list
/v1/warehouse/fbs/return-mile/check → не нужен         → пункты возврата 1060001…1060006
                         \                          /
              /v1/warehouse/fbs/create → operation_id, склад появляется в списке со статусом new
              /v1/warehouse/operation/status → IN_PROGRESS … SUCCESS, result.entity_id — ID склада
              склад переходит в created: в него можно публиковать остатки, для него генерируются заказы
```

- Пункты и слоты — небольшой справочник эмулятора; координаты пунктов — небольшие смещения от переданных.
- Операция завершается через `operationDelaySeconds` по часам кабинета.
- При создании проверяется: пункт сдачи обязателен для `DROP_OFF` и запрещён для `PICK_UP`; пункт и слот — из
  списков выше; пункт возврата передан, если он нужен; телефоны в формате `+7(XXX)XXX-XX-XX`; название не повторяется;
  `cut_in_time` больше 0; рабочие дни без повторов (по умолчанию пн–пт). Ошибка — 400, неизвестный пункт или
  операция — 404.
- Пункт возврата нужен только для `PICK_UP`; для `DROP_OFF` возвраты приходят в тот же пункт. Это решение эмулятора.
- Для крупногабарита (`is_kgt`) сдача только в сортировочный центр, курьер недоступен.
- Поддерживается только `country_code: RU`.
- `/v1/warehouse/fbs/update/drop-off/list` отдаёт пункты, на которые можно перевести существующий склад.
- Созданные склады хранятся в данных кабинета и переживают повторную загрузку конфигурации; событие `reset` их удаляет.

## Остатки

Остаток ведётся по паре «товар — склад»:

| Поле | Что значит |
|---|---|
| `stock` | Свободное количество, которое продавец опубликовал через `/v2/products/stocks`. До первой публикации 0 |
| `reserved` | Сколько товара занято отправлениями склада в статусах `awaiting_registration`, `awaiting_packaging`, `awaiting_deliver` |
| `present` | `stock + reserved` |
| `free_stock` | `stock` |

`/v2/products/stocks` принимает до 100 пар за запрос. Ошибка в отдельной паре не мешает остальным: запрос отвечает
200, а ошибка попадает в `result[].errors`.

| Код | Причина |
|---|---|
| `PRODUCT_NOT_FOUND` | Нет товара с таким `offer_id` или `product_id`; если переданы оба, используется `offer_id` |
| `WAREHOUSE_NOT_FOUND` | Это не FBS-склад кабинета |
| `WAREHOUSE_NOT_ACTIVE` | Склад ещё не в статусе `created` |
| `PRODUCT_NOT_IN_FBS_ASSORTMENT` | Товара нет в `productSkus` |
| `INVALID_STOCK` | Отрицательный остаток |
| `TOO_MANY_REQUESTS` | Пару обновляли меньше 30 секунд назад |

Коды, кроме `TOO_MANY_REQUESTS`, придуманы эмулятором — в описании API Ozon их нет.

`/v2/product/info/stocks-by-warehouse/fbs` отдаёт строку на каждый запрошенный товар и каждый активный склад,
включая нулевые остатки. Нужен хотя бы один фильтр — `sku` или `offer_id`; если есть оба, результаты объединяются.

Публикация перезаписывает `stock` целиком. Если заказ пришёл между тем, как клиент посчитал остаток, и публикацией,
товара окажется «продано больше, чем есть» — как и в настоящем Ozon. Эмулятор этого не предотвращает: так можно
проверить, что клиент учитывает ещё не загруженные заказы.

## Тестовые заказы

Покупателей в эмуляторе нет, поэтому заказы создаёт команда:

```bash
# 5 отправлений каждые 10 минут, всего 50
docker compose exec php-cli php psb ozon:fbs:generate 1001 --batch=5 --every=10 --total=50

# 20 сразу, воспроизводимо
docker compose exec php-cli php psb ozon:fbs:generate 1001 --batch=20 --total=20 --seed=42
```

Заказ создаётся **только из опубликованного свободного остатка**: случайный активный склад с остатком, от 1 до 3
его товаров, по 1–3 штуки, но не больше свободного остатка. Заказанное количество уходит из `stock` в `reserved`.
Метод доставки — случайный из методов склада. Отправление получает статус `awaiting_packaging` и срок отгрузки
через сутки по часам кабинета.

Если остатка нет, команда ничего не создаёт и сообщает об этом. С `--every=0` она на этом заканчивается, с
`--every` больше 0 — ждёт следующего запуска: остаток могут опубликовать позже. `--seed` повторяет тот же выбор
при тех же остатках.

## Отправления

| Метод | Что делает |
|---|---|
| `/v4/posting/fbs/unfulfilled/list` | Незавершённые отправления; фильтры `statuses`, `warehouse_ids`, `delivery_method_ids`, `cutoff_from/to` (вместе с `delivering_date_*` — 400); `limit` до 100; `count` — всего по фильтру |
| `/v4/posting/fbs/list` | Отправления за период `filter.since/to` (по дате создания), те же фильтры и `order_id` |
| `/v3/posting/fbs/get` | Одно отправление. Цена строкой и `currency_code`, как в v3. Дополнительно: `with.product_exemplars` — экземпляры, `with.related_postings` — другие отправления заказа, `with.barcodes` — штрихкоды этикетки |
| `/v2/posting/fbs/get-by-barcode` | Отправление по верхнему или нижнему штрихкоду этикетки |

Продолжение списков — по `cursor`. В эмуляторе это просто смещение следующей страницы, но клиент не должен на это
полагаться: разбирать курсор не нужно.

## Отмена

| Метод | Что делает |
|---|---|
| `/v1/posting/fbs/cancel-reason` | Причины, по которым продавец может отменить эти отправления (только несобранные) |
| `/v2/posting/fbs/cancel-reason/list` | Весь справочник причин: 352, 400, 401, 402, 665–667, с инициатором и признаком доступности |
| `/v2/posting/fbs/cancel` | Отменяет отправление целиком. Для причины 402 «Другое» нужен комментарий. Отправление переходит в `cancelled`, товар возвращается в свободный остаток |
| `/v2/posting/fbs/product/cancel` | Отменяет часть товаров; комментарий обязателен. Отмена всех единиц отменяет отправление. Товар возвращается в свободный остаток |

Частичная отмена доступна отправлениям больше чем с одной единицей товара: отменить единственную единицу — значит
отменить отправление. Названия и номера причин взяты из описания API Ozon; инициатор причин 665–667 и признаки
доступности выбраны эмулятором.

## Сборка

Порядок работы с отправлением, у которого есть требования:

```text
/v6/fbs/posting/product/exemplar/create-or-get → ID экземпляра на каждую единицу товара
/v2/posting/fbs/product/country/set            → если нужна страна изготовления
/v6/fbs/posting/product/exemplar/set           → данные всех экземпляров (полный набор)
/v5/fbs/posting/product/exemplar/status        → validation_in_process … ship_available | ship_not_available
/v4/posting/fbs/ship                           → отправление собрано; результат проверяется через /v3/posting/fbs/get
/v3/posting/fbs/package-label/create → /v2/posting/fbs/package-label/get → PDF этикеток
```

Отправление без требований можно собрать сразу.

### Экземпляры

Экземпляр — одна единица товара в отправлении. `create-or-get` создаёт ID экземпляров один раз и потом возвращает
те же; вместе с ними приходят признаки, что нужно передать: `is_mandatory_mark_needed`, `is_gtd_needed`,
`is_rnpt_needed`, `is_weight_needed` с допустимым диапазоном веса и т. д. После частичной отмены лишние
экземпляры удаляются с конца.

Данные передаются через `set` — всегда полным набором: все товары отправления, все их экземпляры. Ответ `{}`
означает только, что данные приняты на проверку. Проверка занимает `operationDelaySeconds`; пока она идёт,
`status` отвечает `validation_in_process`, а у кодов — `check_status: processing`.

Эмулятор различает **переданные** и **подтверждённые** данные. Переданные не заменяют подтверждённые, пока проверка
не пройдена. До сборки прошедшая проверка сохраняется сразу. После сборки — только после вызова
`/v1/fbs/posting/product/exemplar/update`. `/v3/posting/fbs/get` всегда показывает подтверждённые данные.

`set` сразу отвечает 400, если:

- переданы не все товары или не все экземпляры, есть чужой или повторный `exemplar_id`;
- не хватает обязательных данных: КИЗ, IMEI, УИН, ГТД (или отметки `is_gtd_absent`), РНПТ (или `is_rnpt_absent`), веса;
- передан код, который товару не нужен (например, КИЗ для товара без маркировки), или один тип кода дважды.

Это решение эмулятора: в описании Ozon эти случаи не разобраны.

Ошибки асинхронной проверки (коды придуманы эмулятором):

| Код | Причина |
|---|---|
| `INVALID_MARK_FORMAT` | КИЗ не соответствует формату: `01` + GTIN (14 цифр) + `21` + серийный номер (до 20 символов), затем символ GS (0x1D) и криптохвост. Обратная косая черта не бывает символом кода, поэтому текст `\u001d` вместо самого символа — тоже ошибка формата |
| `CRYPTO_TAIL_REQUIRED` | КИЗ без криптохвоста |
| `DUPLICATE_MARK` | Код повторяется в отправлении или уже подтверждён в другом неотменённом отправлении кабинета |
| `NOT_IN_TURNOVER` | Код из списка `rejectedMarks` сценария — имитация кода, которого нет в обороте |
| `INVALID_IMEI_FORMAT`, `INVALID_JW_UIN_FORMAT` | IMEI — не 15 цифр; УИН — не цифры (до 64) |
| `INVALID_GTD_FORMAT`, `INVALID_RNPT_FORMAT` | ГТД не в формате `NNNNNNNN/NNNNNN/NNNNNNN`; РНПТ — тот же формат и `/N` (до 3 цифр) |
| `WEIGHT_OUT_OF_RANGE` | Вес вне `weight_min…weight_max`: ±20 % веса товара из каталога, в килограммах |

`/v5/fbs/posting/product/exemplar/validate` проверяет только формат кодов, ГТД и РНПТ — сразу, без учёта требований
и других отправлений.

Итоговый `status`: `validation_in_process` — идёт проверка; `ship_available` / `ship_not_available` — можно ли
собирать; после сборки — `update_available`; в других статусах отправления — `update_not_available`.

### Страна изготовления

`/v2/posting/fbs/product/country/list` — справочник эмулятора: Россия, Беларусь, Казахстан, Китай, Турция,
Узбекистан; поиск `name_search` по части названия без учёта регистра.

`/v2/posting/fbs/product/country/set` принимает `product_id` — ID товара в каталоге (как в описании API), а не SKU.
Он снимает требование страны; страна не Россия добавляет требование ГТД (`is_gtd_needed: true`). Это правило эмулятора.

### Сборка

Собрать можно отправление в статусе `awaiting_packaging` с действием `ship` или `ship_with_additional_info`, если
для товаров с требованиями указана страна и подтверждены данные всех экземпляров. Иначе — 400. Реальный Ozon может
принять такой запрос и не собрать отправление; для проверки этого случая есть сценарий `shipFailures`.

- **`/v4/posting/fbs/ship`** собирает всё отправление. Каждая упаковка из `packages` становится отдельным
  отправлением: первая сохраняет номер, следующие получают номера `<номер заказа>-2`, `-3`, … и ссылку на исходное
  в `parent_posting_number`. Сумма упаковок должна точно совпадать с составом. Экземпляры раскладываются по
  упаковкам по порядку. С `with.additional_data` ответ содержит состав и КИЗ собранных отправлений.
- **`/v4/posting/fbs/ship/package`** собирает часть: переданные товары (с `exemplarsIds` — именно эти экземпляры)
  становятся новым собранным отправлением, остальное остаётся несобранным под исходным номером. Если передать всё,
  собирается само отправление. Описание Ozon здесь неоднозначно, эмулятор выбрал простую модель.
- **`/v1/posting/fbs/split`** делит несобранное отправление на две и более части без сборки. Части вместе должны
  содержать ровно товары отправления. Модель эмулятора (номера частей Ozon не описывает): исходное отправление
  становится `cancelled_from_split_pending` и хранит исходный состав, каждая часть получает новый номер заказа
  с `parent_posting_number` и остаётся `awaiting_packaging`; экземпляры раздаются частям по порядку, резерв сохраняется.
- **Многокоробочный товар** (`multiboxSkus`): пока отправление не собрано, `is_multibox: true`; количество коробок
  передаётся в `multi_box_qty` запроса `/v6/fbs/posting/product/exemplar/set` и остаётся в `multi_box_qty` после
  сборки, где `is_multibox` уже `false`. Сборку без количества коробок эмулятор, как и Ozon, не запрещает — товар
  считается упакованным в одну коробку.

Собранное отправление получает статус `awaiting_deliver` и подстатус `posting_not_in_carriage`, действия
`label_download_big`, `label_download_small` и, если есть маркировка, `update_cis`. Товар остаётся в резерве.

## Этикетки

`/v3/posting/fbs/package-label/create` (`posting_numbers`, ответ `tasks` без `result`) создаёт две задачи — большую
(`big_label`) и маленькую (`small_label`) этикетку. `/v2/posting/fbs/package-label/get` показывает ход задачи в
`status.code`: первую половину `operationDelaySeconds` — `pending`, затем `in_progress`, потом `completed` со ссылкой
`file_url` или `error` с `error.code`; непринятые отправления — в `status.unprinted_postings[].message`. Значения
`status.code` документация Ozon не перечисляет — эмулятор берёт их из v1.

Устаревшие `/v2/posting/fbs/package-label/create` (`posting_number`) и `/v1/posting/fbs/package-label/get` (ответ в
`result`) работают до их отключения в Ozon 2.11.2026.

Результат фиксируется при первом запросе после готовности: печатаются собранные отправления, остальные попадают в
`unprinted_postings` с причиной — «The next postings aren't ready» или «Posting is cancelled». Если печатать нечего —
`error` и `NO_POSTINGS_TO_PRINT`. Повторный запрос отдаёт тот же файл.

PDF синтетический и помечен как тестовый: страница на отправление, большая этикетка 75 × 120 мм, маленькая —
58 × 40 мм, штрихкод Code 128. Штрихкоды выбраны эмулятором: нижний — цифры номера отправления, верхний — `%101%`
и нижний. Ссылка действует сутки и перестаёт работать (410), если отправление из файла отменено.

## Отгрузки

Отгрузка (`carriage`) объединяет собранные отправления одного метода доставки на одну дату отгрузки. Дата отгрузки
отправления — дата его `shipment_date`.

1. `/v2/carriage/delivery/list` показывает методы доставки на дату (`filter.departure_date`, по умолчанию сегодня
   по часам кабинета). Фильтр `filter.delivery_method_id` принимает ID метода доставки или ID склада. Для метода видны
   количество ожидаемых и собранных отправлений, отгрузки и ошибки: `NOT_ALL_POSTINGS_PACKAGED`, если собраны не все.
   Пока собранные отправления ждут вне отгрузки, в `carriages` есть строка с `id: 0` и действием `create`.
2. `/v1/carriage/create` создаёт отгрузку в статусе `new` из всех собранных отправлений метода и даты, которые не
   входят в другую отгрузку. Вторую действующую отгрузку на тот же метод и дату создать нельзя. Отправления получают
   подстатус `posting_in_carriage`.
3. `/v1/carriage/set-postings` заменяет состав, только пока отгрузка `new`. Результат — по каждому отправлению:
   `POSTING_NOT_FOUND`, `WRONG_DELIVERY_METHOD_OR_DATE`, `POSTING_NOT_ASSEMBLED`, `POSTING_IN_ANOTHER_CARRIAGE`.
   Убранные отправления возвращаются в `posting_not_in_carriage`.
4. `/v1/carriage/approve` подтверждает отгрузку: статус `formed`. Документы формируются 30 секунд по часам кабинета:
   `/v2/posting/fbs/act/check-status` отвечает `in_process`, затем `ready`, а `/v1/carriage/get` — действиями
   `get_shipping_list` и `get_act_of_acceptance`. Состав — `/v2/posting/fbs/act/get-postings`, текст штрихкода
   отгрузки — `/v2/posting/fbs/act/get-barcode/text` (`OZN` и ID отгрузки). Когда документы готовы,
   `/v2/posting/fbs/act/get-pdf` отвечает файлом PDF (`Content-Type: application/pdf`): тестовый лист отгрузки с номером,
   датой, методом доставки и списком отправлений. До готовности — ошибка 400.
5. `/v1/carriage/cancel` отменяет отгрузку `new` или `formed`: отправления возвращаются в `posting_not_in_carriage`.
   Для закрытой отгрузки метод отвечает с текстом ошибки в `error`.

Передачу водителю имитирует управляющее событие `fbsHandover` (ниже). Принятые отправления переходят в
`delivering` (`posting_transferred_to_courier_service`), их резерв снимается, в списке несобранных они больше не
видны. Отгрузка становится `closed`. Непринятые отправления выходят из отгрузки и ждут следующую. Отменённое после подтверждения
отправление едет с отгрузкой, но остаётся отменённым.

Статус `formed`, коды ошибок состава и штрихкод выбраны эмулятором: в описании API их нет.

## Управляющие события

Как запускать события — в [Тестовый кабинет](cabinet.md#управляющие-события). Для FBS есть:

```json
{"eventId": "fbs-1", "type": "fbsScenario", "shipFailures": 1, "labelFailures": 1, "rejectedMarks": ["0104600000000017..."]}
{"eventId": "fbs-2", "type": "fbsRequirements", "postingNumber": "12345678-0001-1", "requirements": {"mandatory_mark": [910001], "weight": []}}
{"eventId": "fbs-3", "type": "fbsHandover", "carriageId": 1000123, "missingPostings": ["12345678-0001-1"]}
{"eventId": "fbs-4", "type": "fbsMarkChange", "postingNumber": "12345678-0001-1", "exemplarId": 100171, "mark": "0104600000000017..."}
```

- `shipFailures` — следующие N сборок будут приняты (200), но отправление останется в `awaiting_packaging` с
  подстатусом `ship_failed`. Повторная сборка пройдёт.
- `labelFailures` — следующие N заказов этикеток завершатся `error` / `LABEL_GENERATION_FAILED`.
- `rejectedMarks` — коды, которые проверка отклонит как `NOT_IN_TURNOVER`.
- Поля `fbsScenario` можно передавать по отдельности: переданные заменяют прежние значения, остальные сохраняются.
- `fbsRequirements` меняет требования несобранного отправления (только для его товаров). Переданные виды
  заменяются, остальные сохраняются. Виды: `mandatory_mark`, `possible_mark`, `country`, `gtd`, `rnpt`, `weight`,
  `imei`, `jw_uin`.
- `fbsHandover` — водитель забрал подтверждённую отгрузку. `missingPostings` (необязательно) — отправления, которые
  не приняли: они выходят из отгрузки.
- `carriagePassRequired` в `fbsScenario` — новые отгрузки требуют пропуск на въезд: `carriage/get` отдаёт
  `set_arrival_passes`, пропуск создаётся `/v1/carriage/pass/create` (водитель, телефон, госномер, модель обязательны),
  его ID появляется в `arrival_pass_ids`.
- `fbsMarkChange` — продавец меняет КИЗ экземпляра собранного отправления в кабинете, вне Seller API склада. Только
  для отправления в `awaiting_deliver`; `/v3/posting/fbs/get` затем отдаёт новый КИЗ в `mandatory_mark`.
