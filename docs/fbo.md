# FBO: создание поставки

FBO — схема, при которой продавец везёт товар на склад Ozon. В эмуляторе поставка создаётся теми же запросами, что
и в настоящем Seller API: черновик → расчёт → выбор склада и слота → создание → проверка статуса → чтение заявки.
Отдельной команды «создать поставку» нет: так эмулятор проверяет, что клиент правильно проходит всю цепочку.

Что делать с поставкой дальше — грузоместа, этикетки, изменения, приёмка — описано в
[FBO: грузоместа, документы и приёмка](fbo-operations.md).

## Подготовка

1. Загрузите конфигурацию кабинета, например [`fixtures/fbo-basic.json`](../fixtures/fbo-basic.json), и выпустите
   ключ — см. [Тестовый кабинет](cabinet.md).
2. Проверьте доступ: `POST /v1/roles` вернёт список доступных кабинету методов.

В базовом наборе:

- 10 товаров: SKU `910001`–`910010`, артикулы `FBO-TEST-A`–`FBO-TEST-J`, без обязательной маркировки;
- два кластера (`510001` «Тест Москва», `510002` «Тест Казань») со складами `710001` и `710002`;
- точка сдачи для кросс-докинга `710003`;
- маршруты DIRECT, CROSSDOCK и MULTI_CLUSTER, все товары разрешены;
- слоты на ближайшие 7 дней с 10:00, по часу, по времени Москвы;
- асинхронные операции завершаются через 2 секунды, черновик живёт 30 минут.

Справочники FBO в конфигурации:

| Поле | Что задаёт |
|---|---|
| `warehouses` | Склады Ozon: ID, тип (`FULL_FILLMENT`, `SORTING_CENTER`, …), адрес и часовой пояс |
| `clusters` | Кластеры: ID для API v1, `macrolocalId` для API v2 и черновиков, склады кластера |
| `routes` | Маршруты: тип, точка сдачи, кластеры назначения, разрешённые SKU |
| `slots` | Сколько дней вперёд, с какого часа и какой длительности слоты, ёмкость слота, недоступные даты |
| `products[].quant`, `maxQuantity`, `tags`, `supplyTags` | Квант, максимальное количество, теги товара и требования поставки (маркировка, УПД и т. п.) |
| `sellerWarehouses` | Справочник складов продавца для `/v1/warehouse/fbo/seller/list` |
| `timeslotChangesLimit`, `vehicleRequired`, `cargoLimits` | Сколько раз можно перенести слот, нужна ли машина, лимиты грузомест |

## Шаги создания

Все запросы — `POST` с заголовками `Client-Id` и `Api-Key`. Ответ 200 ещё не значит, что операция завершена:
статусы нужно опрашивать.

| Шаг | Метод | Что происходит |
|---|---|---|
| 1. Направление | `/v1/cluster/list` или `/v2/cluster/list`, `/v1/warehouse/fbo/list` | Кластеры и склады из конфигурации. ID из API v1 и v2 разные — не смешивайте их |
| 2. Черновик | `/v1/draft/direct/create`, `/v1/draft/crossdock/create` или `/v1/draft/multi-cluster/create` | Состав сохраняется, возвращается `draft_id` |
| 3. Расчёт | `/v2/draft/create/info` | Сначала `IN_PROGRESS`, затем `SUCCESS` или `FAILED`: доступные склады, требования поставки, принятый и отклонённый состав |
| 4. Состав | `/v1/supply-order/bundle` | Принятые и отклонённые товары по `bundle_id` из расчёта |
| 5. Слот | `/v2/draft/timeslot/info` | Свободные интервалы для выбранных кластеров и складов |
| 6. Создание | `/v2/draft/supply/create` | Черновик, направление, состав и слот проверяются ещё раз, запускается создание |
| 7. Результат | `/v2/draft/supply/create/status` | Статус запрашивается по **`draft_id`**; при успехе — `order_id` |
| 8. Чтение | `/v3/supply-order/list`, `/v3/supply-order/get`, `/v1/supply-order/details`, `/v1/supply-order/bundle` | Заявка, её поставки и полный состав |

Особенности типов поставок:

- **DIRECT** — черновик получает `cluster_info` с товарами, `macrolocal_cluster_id` и `deletion_sku_mode`;
  склад размещения выбирается из результата расчёта и передаётся в `storage_warehouse_id`.
- **CROSSDOCK** — дополнительно `delivery_info` с точкой сдачи.
- **MULTI_CLUSTER** — `clusters_info` на несколько кластеров и `delivery_info`; получается несколько поставок.

`deletion_sku_mode` определяет, что делать, если товар принят не полностью: `PARTIAL` исключает только непринятые
единицы, `FULL` — весь SKU. Эмулятор сохраняет и запрошенный, и принятый состав.

Если к шагу 6 слот уже занят, создание вернёт ошибку — нужно заново запросить слоты. Истёкший черновик не
оживает: создайте новый.

## Что получается

- У заявки (`order`) есть ID, номер, состояние, точка сдачи и слот.
- У каждой поставки (`supply`) — свой `supply_id`, склад размещения и `bundle_id` с полным составом.
- Для MULTI_CLUSTER товары распределены по поставкам так, как в расчёте; сумма по SKU не меняется.
- Грузомест, этикеток и приёмки ещё нет — они появятся на следующих шагах.

## Повторы и сбои

- Повторное создание по тому же черновику отвечает так, как описано в контракте Ozon, в том числе ошибками
  `ORDER_CREATION_IN_PROGRESS` и `ORDER_ALREADY_CREATED`. Эмулятор не превращает повтор в «успех», чтобы
  клиент видел свои ошибки.
- Если ответ потерялся после записи (сбой `phase: after`), результат находится обычным запросом статуса.
  Если до записи — заявка не создаётся. Как настроить сбой — в [Тестовый кабинет](cabinet.md#сбои).
- Перезапуск сервиса не теряет принятые операции.

## Ограничения

- Поддерживается только доставка до точки сдачи (`DROPOFF`); вывоз со склада продавца (`PICKUP`) отклоняется.
- Требования к товарам (теги, маркировка) берутся из конфигурации, а не рассчитываются, как у Ozon.
- Расширенные фильтры видимости товаров не поддерживаются и дают явную ошибку.
- Срок черновика (30 минут) и час до слота как дедлайн изменений — значения эмулятора; у реальных маршрутов
  Ozon они могут отличаться.
